# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

SocialApp is a social web application: an **ASP.NET Core (.NET 10)** backend (`src/API`) using Clean Architecture/DDD/CQRS, a separate **Notifications service** (`src/Notifications/Notifications.API`, PostgreSQL), and an **Angular 21** SPA client (`src/UI`). Real-time chat/presence runs over SignalR. Details: [README.md](README.md), [src/API/README.md](src/API/README.md), [src/UI/README.md](src/UI/README.md), [src/Notifications/README.md](src/Notifications/README.md), and the `docs/` directory (prefer the code when docs disagree with it). [ARCHITECTURE_ENHANCEMENTS.md](ARCHITECTURE_ENHANCEMENTS.md) and `docs/06-improvement-plan.md` describe *planned* work — don't read them as a description of the current code.

## Commands

### Backend (`.NET`, run from repo root unless noted)

```bash
dotnet restore SocialApp.slnx
dotnet build SocialApp.slnx
dotnet test --solution SocialApp.slnx                                               # all unit + integration tests
dotnet test --project test/unit/Domain.Test                                          # a single test project
dotnet test --project test/unit/Application.Test --filter-class "*CreateFriendRequestHandler*"  # a class
dotnet test --project test/unit/Shared.Test --filter-method "*Success*"              # a method
```

- Tests run on **Microsoft.Testing.Platform**, not VSTest: `global.json` sets `"test": { "runner": "Microsoft.Testing.Platform" }`, and `test/Directory.Build.props` makes every test project an `Exe` with `UseMicrosoftTestingPlatformRunner`. As a result, `dotnet test` needs `--solution`/`--project` rather than a bare path, and the VSTest syntax `--filter "FullyQualifiedName~..."` does not work. Use xUnit v3's `--filter-class` / `--filter-method` / `--filter-namespace` / `--filter-trait` / `--filter-query` instead (wildcards allowed at either end).
- `test/Directory.Build.props` explicitly imports the root `Directory.Build.props`. A new `Directory.Build.props` placed deeper in the tree must do the same, or its projects silently lose the warnings-as-errors and nullable settings.
- Integration tests use Testcontainers — SQL Server for `test/integration/API.Test`, PostgreSQL for `test/integration/Notifications.API.Test`. **Docker must be running**, otherwise those tests fail with `DockerUnavailableException` while every unit project still passes. Run the four `test/unit/*` projects when Docker is unavailable.
- Warnings are errors (`Directory.Build.props`: `TreatWarningsAsErrors`, `CodeAnalysisTreatWarningsAsErrors`, `AnalysisMode=All`, `Nullable=enable`) — any new analyzer warning fails the build.
- Run the API: `cd src/API/API && dotnet run` (`https://localhost:5001`, Swagger at `/swagger` in Development; health at `/health/live` and `/health/ready`). On startup, `DatabaseInitializer` applies migrations and seeds the admin and test users **only in Development**; reference data (roles, countries, cities) is seeded in every environment. Production migrations run in `api-deploy.yml`.
- EF Core migrations live in `src/API/Infrastructure/Data/Migrations`; see [scripts/EfCoreMigrations.md](scripts/EfCoreMigrations.md). Apply manually with `dotnet ef database update --project src/API/Infrastructure --startup-project src/API/API`.
- Secrets (never commit): `dotnet user-secrets set "..." "..."` from `src/API/API` for `ConnectionStrings:AppConnection`, `Jwt:Key`, `Cloudinary:*`, `Authentication:Google:*`.
- Full stack via Docker: `docker compose up --build` (API + SQL Server on `1433`, sa password `Password123!`; `notifications-api` on `http://localhost:5010` + `notifications-db` PostgreSQL on `5432`; Aspire Dashboard on `http://localhost:18888` for OTLP traces/metrics/logs).

### Notifications service (`src/Notifications/Notifications.API`)

```bash
docker compose up -d notifications-db                       # PostgreSQL on localhost:5432
dotnet run --project src/Notifications/Notifications.API    # applies migrations at startup in Development
dotnet test --project test/integration/Notifications.API.Test
dotnet ef migrations add <Name> --project src/Notifications/Notifications.API --startup-project src/Notifications/Notifications.API --output-dir Data/Migrations
```

- Shares the main API's **user-secrets store** (same `UserSecretsId` in the csproj) so both validate the same `Jwt:*`. It additionally needs `Intake:ApiKey` and `ConnectionStrings:NotificationsConnection` (`dotnet user-secrets set ... --project src/Notifications/Notifications.API`); missing values fail at startup.
- EF design-time uses `DesignTimeDbContextFactory` with a placeholder connection, so pass `--connection` to `dotnet ef database update`. Start each new migration file with `// <auto-generated />` so analyzers (warnings-as-errors) skip it.

### Database seeding (`tools/SeedDB`)

```bash
dotnet run --project tools/SeedDB -- --connection "<connection-string>" --users 100 --friends-per-user 10 --posts-per-user 10
dotnet run --project tools/SeedDB -- --connection "<connection-string>" --users 0 --reset   # reset only
```

Fills a database with generated users, accepted friendships and posts. It composes the app's own `AddInfrastructureServices` (adding the Identity registration the API host owns) and refuses to run unless the schema, cities and roles are already present — start the API once, or apply `scripts/seed_essential_data.sql`, first. Seeded logins use the `@seed.local` email domain and the password `Pwd12345`; `--reset` deletes only rows carrying that marker, so hand-made test data survives. Exit codes: `2` bad arguments, `3` prerequisite failure, `4` cancelled.

`scripts/seed-bench.ps1 -Scale <small|medium|large|xlarge|xxlarge> [-Reset] [-Connection ...]` wraps SeedDB with fixed benchmark scales. It defaults to the docker compose database. The scale table lives in the script's `$scales` hashtable and in `docs/01-getting-started.md`; keep the two in sync.

### Benchmarks (`benchmarks/API`)

```bash
docker compose up -d   # SQL Server on localhost:1433
dotnet run -c Release --project benchmarks/API/API -- --filter '*PostQueriesBenchmark*'
```

BenchmarkDotNet suite measuring handler → repository → EF Core → SQL Server, excluding the HTTP pipeline. It is part of `SocialApp.slnx`, so it builds with the solution, but `dotnet test` never runs it. Use `-c Release`, since BenchmarkDotNet rejects Debug builds. Configure it with `SOCIALAPP_BENCHMARK_CONNECTION` / `_USER_ID` / `_POST_ID`. Like SeedDB, `BenchmarkHost` composes the real `AddInfrastructureServices`, so DI changes propagate on their own. See [benchmarks/README.md](benchmarks/README.md) for what the numbers do and don't mean. Output goes to the gitignored `BenchmarkDotNet.Artifacts/`. Don't write benchmark numbers into source comments.

## Architecture

### Backend layering (`src/API`, Clean Architecture — dependencies point inward)

```
Domain/          Aggregates, domain rules & exceptions. Zero external dependencies.
Application/     CQRS commands/queries + handlers, DTOs, repository/service interfaces.
Infrastructure/  EF Core DbContext, repositories, identity/token services, Cloudinary.
API/             ASP.NET Core host: controllers, SignalR hubs, filters, middleware, DI wiring.
Shared/          Cross-cutting: Result<T>, Specification, Pagination, EntityBase.
```

- **CQRS dispatch** uses the [`Mediator`](https://github.com/martinothamar/Mediator) *source generator* (`Mediator.SourceGenerator`) — **not MediatR**, despite `docs/02-architecture.md`. Each use case is a vertical slice under `Application/Features/<Feature>/<UseCase>/`: a `record XCommand(...) : ICommand<Result<T>>` (or `IQuery<...>`) plus `class XHandler : ICommandHandler<XCommand, Result<T>>` whose `Handle` returns **`ValueTask`**. Follow that pairing instead of adding generic service methods.
- **Two user id spaces — the most common source of bugs here.** `ApplicationUser.Id` (int, from `EntityBase`) is the domain/"public" id and is what the JWT carries as `NameIdentifier`; `ICurrentUserService.GetPublicId()` returns it. `ApplicationUser.IdentityId` (string) links to the ASP.NET Identity `IdentityUser` and is assigned once via `AssociateWithIdentity`. Identity/role operations need the Identity id or a `RoleId`; domain lookups need the int id. Never pass one where the other is expected.
- **Result pattern, not exceptions, for expected failures.** `Shared/Results/Result.cs` exposes status factories (`Success`, `Created`, `NotFound`, `Forbidden`, `Unauthorized`, `Conflict`, `Error`, `CriticalError`, `Unavailable`, `NoContent`); `IsSuccess` is true only for `Ok`/`Created`/`NoContent`. Handlers catch `DomainException` and return the matching status. Controllers inject `IMediator` + `ProblemDetailsFactory` and map each failure branch explicitly (`problemDetailsFactory.CreateProblemDetails(HttpContext, status, title, detail: string.Join("; ", result.Errors))`) — there is no shared Result→`ActionResult` mapper, so match the surrounding controller. Reserve thrown exceptions for genuine invariant violations inside `Domain`.
- **Aggregate roots** (`IAggregateRoot`): `ApplicationUser` (owns `Post`, `UserPicture`), `DirectChat` (owns `Message`), `Friend`, `FriendRequest`, `Picture`, `RefreshToken`; `Domain/ReferenceData` holds `City`/`Country`/`Region`. Private setters plus guarded constructors/factories (`FriendRequest.Create(...)`, `user.AddPost(...)` which returns the new `Post`) — child entities are never constructed or mutated from outside their root.
- **Domain events are scaffolding only.** `Shared/DomainEventBase.cs`, `IHasDomainEvents.cs` and `HasDomainEvents.cs` exist but nothing outside `Shared/` references them, and `UnitOfWork.CommitAsync` only calls `SaveChangesAsync`. There is no dispatcher — raising an event today fires nothing; wire dispatch first.
- **Repository + Unit of Work**: persistence goes through `IUnitOfWork.<X>Repository` (`ApplicationUser`, `Picture`, `DirectChat`, `FriendRequest`, `Friend`, `City`) and `CommitAsync`; explicit transactions via `BeginTransactionAsync`/`CommitTransactionAsync`/`RollbackTransactionAsync`. `CachedUserRepository` decorates the user repository with `IMemoryCache`.
- **Specification pattern** (`Shared/Specification` + `SpecificationEvaluator`, plus `IFilterSpecification` for predicate-only filters) shapes reusable queries, e.g. `UserWithPicturesSpecification`, `UserByIdentityFilter`.
- **Validation**: FluentValidation validators (`Features/<X>/Validators`) run through a globally registered `ValidationFilter` MVC filter — add a validator beside a new request model rather than hand-checking in the handler.
- **Dapper is one narrow path**, not a general read strategy: `FriendRequestsRepository` calls the `GetFriendRequestedUsersDTO` stored procedure. The procs themselves are created by EF migrations (the `*StoredProcedure` migrations). Everything else uses EF Core.
- **SignalR**: `OnlineUsersHub` (`hubs/presence`) and `ChatHub` (`hubs/message`). `JwtBearerEvents.OnMessageReceived` lifts the token from the `access_token` query string for paths under `/hubs` (browsers can't set `Authorization` on a WebSocket upgrade). Presence/group state lives in the in-memory singletons `OnlineUsersStore` and `DirectChatGroupsStore` — **single-instance only**; anything assuming shared state across replicas needs a backplane first.
- **Host composition**: `src/API/API/DependencyInjection.cs` groups registrations into `AddGenericServices` (memory cache, CORS `AllowSpecificOrigin` from `Cors:AllowedOrigins`, Swagger + XML comments, health checks, SignalR, Mediator, `LogUserActivity`), `AddSecurity` (global fixed-window rate limiter, 100 req/min partitioned by user name or Host), `AddErrorHandling` (`ProblemDetails` with a `requestId` extension, `ValidationFilter`, `GlobalExceptionHandler`), `AddObservability` (OpenTelemetry traces/metrics/logs, OTLP exporter in Development), `AddIdentity` (Identity core, JWT bearer, policies `RequireAdminRole` / `RequireModeratorOrAdmin`, role names in `Shared/Constants/RolesNameValues`). Infrastructure services register in `src/API/Infrastructure/DependencyInjection.cs`. Add new registrations to the matching group, not to `Program.cs`.
- **Central package management**: NuGet versions live only in `Directory.Packages.props`; project files reference package names without versions.

### Notifications service (`src/Notifications/Notifications.API`)

Deliberately **not** Clean Architecture: one project with feature folders (`Features/Push`, `Channels/SignalR`, `Deliveries`, `Data`, `Entities`), minimal-API endpoints, plain handler classes (no Mediator), `GlobalUsings.cs`, and EF Core on **Npgsql with snake_case naming**. Registrations are grouped in its own `DependencyInjection.cs` (`AddGenericServices` / `AddErrorHandling` / `AddObservability` / `AddAuth` / `AddDatabase` / `AddDelivery`). Its README is the spec; the essentials:

- **Accept now, deliver later.** `POST /notifications/push` (header `X-Api-Key`, checked by `ApiKeyEndpointFilter`) writes the notification plus one `Delivery` row per recipient × enabled channel in one transaction and returns `202`; nothing is sent during the request. `eventId` is unique, so a retried push is a no-op (`duplicate: true`).
- **One background worker per channel** claims due rows (`FOR UPDATE SKIP LOCKED` + a lease stored in `next_attempt_at`), calls `INotificationChannel.SendAsync`, and records the outcome. Statuses: `Pending → Processing → AwaitingAck → Delivered`, plus `Parked` (recipient offline; not an attempt; replayed on their first connect) and terminal `Failed` / `Expired`. A cleanup worker expires long-parked rows and deletes old finished notifications.
- **At-least-once**: SignalR clients get `ReceiveNotification` and must call `Acknowledge(eventId)`; no ack within `AckTimeout` → re-send. Clients must de-dupe by `eventId`.
- New channel: implement `INotificationChannel`, register with `services.AddNotificationChannel<T>("name")` in `AddDelivery`; options bind from `Delivery:Channels:<name>:*`.
- Recipients are the main API's int user id from the JWT `nameid` claim (`Context.UserIdentifier` on `/hubs/notifications`). Presence (`PresenceTracker`) is in memory → **single instance only**, same caveat as the API's hubs.
- The main API does **not** call this service yet; chat notifications still go through the API's own `MessageNotifier`.

### Frontend (`src/UI/src/app`)

- **Zoneless change detection** (`provideZonelessChangeDetection()` in `app.config.ts`) — there is no zone.js. Code relying on implicit change detection after an async callback won't refresh the view; use signals or explicit updates.
- Angular 21 naming: `post-item/post-item.ts` exports `class PostItem` (no `.component.ts`, no `Component` suffix); standalone components with per-component `imports`; Angular Material + CDK for UI. Existing code mixes decorator `@Input()` with newer signal APIs — match the file you're editing.
- Feature folders: `auth/` (login/signup, Google Sign-In, guards, `interceptors/auth-interceptor` attaching the JWT), `direct-chat/`, `home/`, `newsfeed/` (`create-post`, `newsfeed-page`, `post-list`, `post-item`), `user/` (`profile`, `user-pictures`), `shared/` (`global-loader`, `nav-bar`, `models/`, `services/` incl. `chat-hub.service`, `data-reference.service`, `loader`). Per-environment API/hub URLs live in `src/environments/`.

### Tests

- `test/unit/{Domain,Application,Infrastructure,Shared}.Test` — xUnit **v3** + NSubstitute, one project per backend layer, covering handler happy/error paths and aggregate invariants. Use `TestContext.Current.CancellationToken` in `IAsyncLifetime` setup (the v3 convention already used here). `Infrastructure.Test` uses `RichardSzalay.MockHttp`; `Application.Test`/`Infrastructure.Test` use the EF Core in-memory provider.
- `test/integration/API.Test` — `WebApplicationFactory` (`Infrastructure/WebAppFactory.cs`) + Testcontainers SQL Server + WireMock.Net with `MockGoogleCredentialValidator` stubbing Google OAuth; routes centralized in `Infrastructure/Routes.cs`, all tests in one xUnit collection.
- `test/integration/Notifications.API.Test` — `WebAppFactory` with Testcontainers PostgreSQL, a test API key/JWT key, and shortened delivery timings (`PollInterval`, `AckTimeout`, `MaxAttempts`) so retry, ack-timeout and give-up paths finish within a test. It drives real `SignalR.Client` connections over the test server. `Deliveries/DeliveryPolicyTests` are pure unit tests that live in this integration project (`InternalsVisibleTo` exposes the service's internals).
- **Duplicate integration test classes exist**: `Features/AuthTests.cs` and `Features/UsersTests.cs` are stale near-copies of `Features/Auth/AuthTests.cs` and `Features/Users/UsersTests.cs` (different namespaces, so both compile and both run). The nested files are the fuller versions — edit those, then decide whether the flat copy needs the same change or deletion.
- Untracked build leftovers at repo root (`tests/`, `scratch/`, `bin/`, `obj/`) are not in `SocialApp.slnx` — ignore them.

## Git conventions (from CONTRIBUTING.md)

- Commit format: `<type>(<scope>): <short summary>` — types: `feat, fix, refactor, docs, test, chore, perf, build, ci, style`. Scope is `api`, `ui`, or a layer (`domain`, `application`, `infrastructure`); omit scope when a change spans both `src/API` and `src/UI`. Reference tracked issues with a footer `Refs #123`.
- Branch format: `<type>/<short-kebab-description>` or `<type>/<issue-number>-<short-kebab-description>`, types: `feature/, fix/, chore/, docs/, refactor/, release/, hotfix/`.
- Flow: `feature/*`/`fix/*` branch from and merge into `develop` (default branch, CI build target). `release/*` branches from `develop`, merges to `master` and back to `develop`. `hotfix/*` branches from `master`, merges to both. Pushes to `master` trigger deploys — don't push there directly outside that flow.
